# AKS Azure Platform Workloads User Resource

This Porter bundle deploys platform workloads (Jenkins, Gitea, Nexus) on an existing AKS cluster within Azure TRE.

## Local Testing

For local development and testing of this Porter bundle, you can use the provided `porter-local.yaml` configuration with Minikube instead of requiring a full Azure environment.

### Prerequisites

- Docker Desktop or Docker Engine
- Minikube
- Porter CLI
- kubectl

### Setup Local Testing Environment

1. **Start Minikube**:
   ```bash
   minikube start
   ```

2. **Set up local Docker registry**:
   ```bash
   # Start a local registry
   docker run -d -p 5001:5000 --name registry registry:2
   
   # Configure Minikube to use local registry
   minikube addons enable registry
   ```

3. **Build the local Porter bundle**:
   ```bash
   # Build using the local configuration
   porter build --file porter-local.yaml
   ```

### Running Local Tests

The `porter-local.yaml` configuration provides a simplified testing environment that:

- Creates mock outputs for AKS DNS suffix and private DNS zone
- Tests template processing with `envsubst` 
- Validates environment variable substitution in Helm values templates
- Debugs the Porter bundle workflow without requiring Azure resources

**Execute local test**:
```bash
porter install test-bundle --file porter-local.yaml
```

### What the Local Test Does

1. **Mock Output Creation**: Creates example output files that simulate what would be generated by the actual AKS infrastructure:
   - `aks_subdomain_suffix`: Example Subdomain suffix
   - `aks_private_dns_zone`: Example private DNS zone
   - `aks_agent_pool`: Example agent pool name

2. **Template Processing Validation**: Tests the critical template processing workflow:
   - Reads Porter outputs from files (runtime behavior)
   - Sets environment variables for `envsubst`
   - Processes `values-template.yaml` to generate `values.yaml`
   - Validates variable substitution works correctly

3. **Debug Output**: Displays the processed values and confirms template variables are properly substituted.

### Key Testing Insights

- **Porter Parameters vs Outputs**: Parameters are available at template time (`${{ bundle.parameters.name }}`), while outputs must be read from files at runtime (`$(cat /cnab/app/outputs/file)`)
- **Environment Variable Processing**: Use `envsubst` for dynamic Helm value generation from templates
- **File-based Communication**: Porter outputs are written to `/cnab/app/outputs/` and must be read as files in bash scripts

### Troubleshooting Local Tests

**Common Issues**:

1. **envsubst command not found**: Ensure `gettext-base` package is installed in the Docker image
2. **Template variables not substituted**: Check that environment variables are set before calling `envsubst`
3. **Output files not found**: Verify outputs are created in the correct step before attempting to read them

**Debug Commands**:
```bash
# Check Porter bundle structure
porter explain --file porter-local.yaml

# View detailed execution logs
porter install test-bundle --file porter-local.yaml --debug

# Clean up test installation
porter uninstall test-bundle --file porter-local.yaml
```

### Transitioning to Production

After validating locally with `porter-local.yaml`, the same template processing patterns are applied in the main `porter.yaml` for production deployment with actual Azure resources.

The key difference is that production uses Terraform to provision real AKS infrastructure and outputs actual DNS configurations, while local testing uses mock values to validate the template processing workflow.
